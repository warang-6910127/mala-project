# Test Plan: ระบบสั่งกาแฟที่โต๊ะด้วย QR Code

> สร้างเมื่อ: 2026-08-15 | สถานะ: Draft

## วัตถุประสงค์ (Objective)

- ทดสอบ flow หลักของฟีเจอร์ Must have "สั่งกาแฟที่โต๊ะด้วย QR Code" ให้ครอบคลุมเกณฑ์การยอมรับทั้ง 4 ข้อใน [[../../01-requirements/01-spec/20260802-001-dine-in-qr-table-ordering|สเปคเต็ม]] และ journey ของลูกค้า/บาริสต้าใน [[../../02-design/01-prototypes/user-journey|user-journey]]
- ครอบคลุม privacy notice ตาม [[../../01-requirements/01-spec/20260802-003-log-retention-pdpa-compliance|สเปค PDPA/Log Retention]] เนื่องจากเป็นขั้นตอนหนึ่งใน flow เดียวกัน (journey ขั้นตอน C)

## ขอบเขตการทดสอบ (Scope)

### สิ่งที่ทดสอบ (In scope)

- การสแกน QR code เพื่อเข้าสู่หน้าสั่งอาหารที่ระบุหมายเลขโต๊ะถูกต้อง
- การแสดง privacy notice ก่อนสั่ง/จ่ายเงิน
- การเลือกเมนู ยืนยันออเดอร์ และชำระเงินในขั้นตอนต่อเนื่องเดียวกัน
- เงื่อนไขที่ออเดอร์จะ/จะไม่ถูกส่งเข้า KDS ตามผลการชำระเงิน
- การแสดงออเดอร์บนจอ KDS แบบเรียลไทม์ พร้อมหมายเลขโต๊ะและรายการอาหาร

### สิ่งที่ไม่ทดสอบ (Out of scope)

- Sales dashboard ([[../../01-requirements/01-spec/20260802-002-sales-dashboard|Sales Dashboard]]) — มี test plan แยกต่างหากในอนาคต
- Retention/anonymize log หลัง 90 วัน และช่องทาง manual สำหรับสิทธิ์เจ้าของข้อมูล — เป็นกระบวนการระยะยาว/manual ที่ไม่ได้ทดสอบผ่าน flow การสั่งอาหารนี้
- UX ฝั่งลูกค้าเมื่อชำระเงินไม่สำเร็จ (retry/ข้อความแจ้งเตือน) — **ยังไม่มีสเปคระบุไว้** ดูหมายเหตุช่องว่างด้านล่าง

## Test Data / เงื่อนไขก่อนทดสอบ

- QR code ทดสอบของโต๊ะอย่างน้อย 1 โต๊ะ (เช่น โต๊ะ 5) ที่ยังไม่มีออเดอร์ค้างอยู่
- บัญชี/sandbox สำหรับช่องทางชำระเงิน QR พร้อมเพย์ ที่จำลองได้ทั้งกรณีจ่ายสำเร็จและจ่ายไม่สำเร็จ
- เมนูทดสอบอย่างน้อย 2 รายการที่เปิดขายอยู่
- จอ KDS ที่เข้าถึงได้ระหว่างการทดสอบเพื่อสังเกตผลแบบเรียลไทม์

## หมายเหตุช่องว่าง (Known Gap)

- TC-006 ทดสอบไม่ได้อย่างสมบูรณ์ในตอนนี้ เนื่องจาก [[../../01-requirements/01-spec/20260802-001-dine-in-qr-table-ordering|สเปค 001]] ยืนยันเพียงว่าออเดอร์ที่จ่ายไม่สำเร็จต้องไม่เข้า KDS แต่ไม่ได้ระบุ UX ฝั่งลูกค้า (ข้อความแจ้งเตือน/จำนวนครั้งที่ retry ได้) — ตรงกับช่องว่างที่ [[../../02-design/01-prototypes/user-journey|user-journey-writer]] เคยตั้งข้อสังเกตไว้แล้ว ต้องชี้แจงกับเจ้าของร้านก่อนจะปิด test case นี้ได้ครบถ้วน
- prototype [[../../02-design/01-prototypes/prototypes/v1/03-customer-payment-result|หน้าผลการชำระเงิน]] (เพิ่มเข้ามาใน v1 หลังจากเขียน test plan ฉบับนี้) ยืนยันช่องว่างเดิมซ้ำอีกครั้ง — ปุ่ม "ลองชำระเงินใหม่" ในไวร์เฟรมเป็นเพียง placeholder ขั้นต่ำสุด ไม่ได้ยืนยันจำนวนครั้งที่ retry ได้หรือข้อความแจ้งเตือนที่แน่นอน จึงยังไม่ปิดช่องว่างนี้ และ TC-006 ยังคงสถานะ Blocked เช่นเดิม
