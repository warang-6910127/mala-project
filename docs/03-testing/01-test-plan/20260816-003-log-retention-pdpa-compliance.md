# Test Plan: การเก็บ Log และการปฏิบัติตาม PDPA

> สร้างเมื่อ: 2026-08-16 | สถานะ: Draft

## วัตถุประสงค์ (Objective)

- ทดสอบ flow ให้ครอบคลุมเกณฑ์การยอมรับทั้ง 4 ข้อใน [[../../01-requirements/01-spec/20260802-003-log-retention-pdpa-compliance|สเปคเต็ม]] ซึ่งเป็นสเปคเชิง data/privacy ที่ตัดขวางฟีเจอร์ "สั่งกาแฟที่โต๊ะด้วย QR Code" และ "Sales Dashboard"
- ครอบคลุม journey "ลูกค้าขอใช้สิทธิ์ข้อมูลส่วนบุคคล (PDPA)" ใน [[../../02-design/01-prototypes/user-journey|user-journey]] โดยตรง
- Privacy notice (journey ขั้นตอน C ใน flow "ลูกค้าสั่งกาแฟที่โต๊ะด้วย QR Code") **ไม่มี test case ซ้ำในเอกสารนี้** — ทดสอบไว้แล้วที่ TC-002 ใน [[20260815-001-dine-in-qr-table-ordering|test plan: สั่งกาแฟที่โต๊ะด้วย QR Code]] เนื่องจากเป็นขั้นตอนหนึ่งใน flow เดียวกันกับการสั่งอาหาร

## ขอบเขตการทดสอบ (Scope)

### สิ่งที่ทดสอบ (In scope)

- การลบหรือ anonymize log ทั้ง 3 ประเภท (order log, payment transaction log, table/session log) ที่มีอายุเกิน 90 วัน
- การไม่ลบ/ไม่ anonymize log ที่ยังไม่ครบ 90 วัน (boundary check ป้องกันการลบก่อนกำหนด)
- ช่องทาง manual (ติดต่อพนักงาน/เจ้าของร้าน) ให้ลูกค้าขอลบ/ขอดูข้อมูลออเดอร์ของตัวเอง ว่าใช้งานได้จริงแบบ end-to-end

### สิ่งที่ไม่ทดสอบ (Out of scope)

- Privacy notice ก่อนสั่ง/จ่ายเงิน — มี test case อยู่แล้วที่ TC-002 ใน [[20260815-001-dine-in-qr-table-ordering|test plan: สั่งกาแฟที่โต๊ะด้วย QR Code]] ไม่สร้างซ้ำ
- เกณฑ์การยอมรับข้อ 4 (การระบุความเสี่ยง retention 90 วัน เทียบกฎหมายบัญชี/ภาษี 5 ปี) — เป็นเกณฑ์เชิงความครบถ้วนของเอกสาร (document-completeness) ที่ตรวจสอบได้จากการอ่านสเปคเท่านั้น ไม่ใช่พฤติกรรมของระบบที่ทดสอบด้วย runtime test case ได้ ดูรายละเอียดใน "Acceptance Criteria Coverage" และ "หมายเหตุช่องว่าง" ด้านล่าง
- Consent management platform, audit log การเข้าถึง dashboard, DPA กับ payment gateway, ฟีเจอร์ self-service ลบ/ดาวน์โหลดข้อมูล, แผนรับมือ data breach — ระบุไว้ชัดเจนแล้วว่าเป็น Out of scope ใน [[../../01-requirements/01-spec/20260802-003-log-retention-pdpa-compliance|สเปค]] จึงไม่ทดสอบ
- Sales dashboard และการสั่งอาหารด้วย QR Code — มี test plan แยกต่างหาก ([[20260816-002-sales-dashboard|test plan: Sales Dashboard]], [[20260815-001-dine-in-qr-table-ordering|test plan: QR Table Ordering]])

## Test Data / เงื่อนไขก่อนทดสอบ

- ชุดข้อมูล log ทดสอบครบทั้ง 3 ประเภท (order log, payment transaction log, table/session log) โดยแต่ละประเภทต้องมีอย่างน้อย:
  - รายการที่มี timestamp **เกิน 90 วัน** จากวันทดสอบ (เช่น ย้อนหลัง 91+ วัน) เพื่อตรวจการลบ/anonymize
  - รายการที่มี timestamp **ยังไม่ถึง 90 วัน** (เช่น ย้อนหลัง 1 วัน และย้อนหลัง 89 วัน) เพื่อตรวจว่ายังไม่ถูกลบก่อนกำหนด
- รายการ log แต่ละรายการต้องมีข้อมูลที่ระบุตัวตนลูกค้าได้ (เช่น หมายเลขโต๊ะ, ข้อมูลการชำระเงินที่เชื่อมโยงกับออเดอร์) เพื่อตรวจสอบว่าหลังลบ/anonymize แล้วไม่มีข้อมูลระบุตัวตนหลงเหลือ
- ช่องทางติดต่อพนักงาน/เจ้าของร้านที่ระบุไว้จริง (เช่น เบอร์โทร/แจ้งหน้าร้าน) พร้อมพนักงาน/เจ้าของร้านที่รับทราบขั้นตอน manual สำหรับคำขอ PDPA
- ออเดอร์ทดสอบอย่างน้อย 1 รายการที่ผูกกับลูกค้า/โต๊ะที่ระบุตัวได้ เพื่อใช้เป็นข้อมูลจำลองคำขอ "ขอลบ/ขอดูข้อมูลออเดอร์ของตัวเอง"

## หมายเหตุช่องว่าง (Known Gap)

- เกณฑ์การยอมรับข้อ 4 (การระบุความเสี่ยง retention 90 วัน เทียบกฎหมายบัญชี/ภาษี 5 ปี) **ไม่ใช่ช่องว่างที่ต้องปิด** — เป็นเกณฑ์เชิงเอกสาร (document review) ที่ satisfied แล้วตั้งแต่ตอนเขียนสเปค จึงไม่มี test case แบบ runtime สำหรับข้อนี้โดยเจตนา
- บริบทความเสี่ยงที่สเปคระบุไว้ (คัดลอกจากสเปคเพื่อการอ้างอิง ไม่ใช่ gap ที่ต้องแก้ในแผนทดสอบนี้): กฎหมายบัญชี/ภาษีของไทยกำหนดให้เก็บเอกสารที่เกี่ยวข้องกับบัญชีอย่างน้อย 5 ปี แต่เจ้าของร้านยืนยันเลือกใช้ retention 90 วันเท่ากันทุกประเภท log อย่างจงใจเพื่อความเรียบง่าย — หากมีการตรวจสอบภาษีหรือข้อพิพาททางบัญชีในอนาคต เจ้าของร้านต้องทบทวนเรื่องนี้กับนักบัญชีของร้านอีกครั้งก่อนที่ log จะถูกลบไปจริง (ดู [[../../01-requirements/01-spec/20260802-003-log-retention-pdpa-compliance|สเปค 003]] กฎ "หมายเหตุความเสี่ยงที่รับทราบแล้ว")
