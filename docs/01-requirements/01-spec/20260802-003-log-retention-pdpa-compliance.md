# การเก็บ Log และการปฏิบัติตาม PDPA

> สร้างเมื่อ: 2026-08-02 | สถานะ: Backlog

## บริบท / ที่มา (Background)

- ระบบ [[20260802-001-dine-in-qr-table-ordering|ระบบสั่งกาแฟที่โต๊ะด้วย QR Code]] และ [[20260802-002-sales-dashboard|Dashboard ดูยอดขาย]] เก็บข้อมูลออเดอร์และการชำระเงินของลูกค้าอยู่แล้วโดยปริยาย (order log, payment transaction log, table/session log) แต่ยังไม่มีสเปคใดกำหนดว่าจะเก็บ log เหล่านี้นานแค่ไหน และยังไม่มีการพูดถึงข้อกำหนดตาม PDPA (พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล) เลย
- เอกสารนี้เป็นข้อกำหนดเชิง data/privacy ที่ตัดขวางทั้งสองฟีเจอร์ข้างต้น (ไม่ผูกกับฟีเจอร์ใดฟีเจอร์หนึ่งโดยเฉพาะ) จึงแยกเป็นเอกสารต่างหาก
- หลักการสำคัญที่เจ้าของร้านย้ำ: **"ทำเท่าที่จำเป็น"** — ไม่ต้องการสร้างระบบ compliance ที่ใหญ่โตเกินขนาดร้าน ให้ทำเฉพาะสิ่งที่จำเป็นต่อการดำเนินธุรกิจและปฏิบัติตามกฎหมายในระดับพื้นฐาน

## ขอบเขต (Scope)

### สิ่งที่ต้องทำ (In scope)

- กำหนด retention period ของ log 3 ประเภท ได้แก่ order log, payment transaction log, table/session log
- ลบหรือ anonymize log หลังพ้นระยะเวลาที่กำหนด (ระบุเป็นกฎทางธุรกิจ ไม่ลงรายละเอียดกลไกทางเทคนิค)
- แสดงประกาศความเป็นส่วนตัว (privacy notice) แบบสั้นๆ ให้ลูกค้าเห็นตอนสแกน QR ก่อนสั่ง/จ่ายเงิน
- กำหนดฐานทางกฎหมาย (legal basis) สำหรับการเก็บข้อมูลออเดอร์/การชำระเงิน
- เปิดช่องทางแบบ manual ให้ลูกค้าติดต่อร้านเพื่อขอใช้สิทธิ์เกี่ยวกับข้อมูลส่วนบุคคลของตัวเอง

### สิ่งที่ไม่ทำ (Out of scope)

- Consent management platform หรือระบบจัดการ consent ที่ซับซ้อน — ใช้แค่ privacy notice แบบข้อความล้วน
- Audit log แยกสำหรับการเข้าถึง sales dashboard — ไม่ทำในเวอร์ชันนี้
- Data Processing Agreement (DPA) แบบทางการกับผู้ให้บริการ QR พร้อมเพย์/payment gateway — ไม่ทำในเวอร์ชันนี้
- ฟีเจอร์ self-service ให้ลูกค้าลบ/ดาวน์โหลดข้อมูลตัวเองผ่านระบบ — ใช้ manual process แทน (ติดต่อพนักงาน/เจ้าของร้าน)
- แผนรับมือ data breach แบบเป็นทางการ — ไม่ทำในเวอร์ชันนี้ (อาจพิจารณาเป็น requirement แยกในอนาคตถ้าจำเป็น)
- การแยก retention period ของ payment log ตามกฎหมายบัญชี/ภาษี (5 ปี) — ตัดสินใจแล้วว่าใช้ retention เดียวกันทั้งหมด (90 วัน) ทุกประเภท log (ดูความเสี่ยงที่ระบุไว้ในกฎทางธุรกิจด้านล่าง)

## User Story / Use Case

- ในฐานะลูกค้าที่สแกน QR เพื่อสั่งอาหาร ฉันต้องการเห็นประกาศสั้นๆ ว่าร้านเก็บข้อมูลอะไรของฉันบ้างและเก็บไปทำไม เพื่อให้ทราบก่อนที่จะสั่งและจ่ายเงิน
- ในฐานะลูกค้า ฉันต้องการช่องทางติดต่อร้านเพื่อขอลบหรือขอดูข้อมูลออเดอร์ของตัวเอง หากต้องการใช้สิทธิ์ตาม PDPA
- ในฐานะเจ้าของร้าน ฉันต้องการให้ log ของออเดอร์/การชำระเงิน/โต๊ะ ถูกลบหรือ anonymize โดยอัตโนมัติหลังพ้นระยะเวลาที่กำหนด เพื่อลดความเสี่ยงด้านข้อมูลส่วนบุคคลโดยไม่ต้องดูแลเอง

## กฎทางธุรกิจ (Business Rules)

- **Retention period**: เก็บ log ทั้ง 3 ประเภท (order log, payment transaction log, table/session log) เป็นระยะเวลา **90 วัน (3 เดือน)** นับจากวันที่เกิดรายการ ใช้ระยะเวลาเดียวกันทั้งหมด ไม่แยกตามประเภท log
- **หมายเหตุความเสี่ยงที่รับทราบแล้ว**: กฎหมายบัญชี/ภาษีของไทยกำหนดให้เก็บเอกสารที่เกี่ยวข้องกับบัญชีอย่างน้อย 5 ปี เจ้าของร้านได้รับแจ้งข้อมูลนี้แล้วและ**ยืนยันเลือกใช้ retention 90 วันเท่ากันทุกประเภท log อย่างจงใจ** (ไม่ใช่ความไม่รู้) เพื่อให้ระบบเรียบง่าย — หากในอนาคตมีการตรวจสอบภาษีหรือข้อพิพาททางบัญชี **ให้เจ้าของร้านทบทวนเรื่องนี้กับผู้ทำบัญชี/นักบัญชีของร้านอีกครั้ง** ก่อนที่ log จะถูกลบไปจริง
- **การลบ/anonymize**: เมื่อ log ครบกำหนด 90 วัน ต้องลบหรือ anonymize ข้อมูลนั้น ไม่คงข้อมูลที่ระบุตัวตนลูกค้าได้ไว้เกินระยะเวลาที่กำหนด
- **Privacy notice**: ต้องแสดงประกาศความเป็นส่วนตัวแบบข้อความสั้นให้ลูกค้าเห็นในขั้นตอนสแกน QR ก่อนที่จะสั่ง/จ่ายเงิน โดยต้องระบุอย่างน้อย (1) ข้อมูลที่เก็บ ได้แก่ ออเดอร์ การชำระเงิน และหมายเลขโต๊ะ และ (2) วัตถุประสงค์ที่เก็บ ได้แก่ เพื่อประมวลผลออเดอร์ และเพื่อวิเคราะห์ยอดขาย
- **ฐานทางกฎหมาย (legal basis)**: ใช้ฐาน "จำเป็นเพื่อปฏิบัติตามสัญญา" (contract necessity) สำหรับข้อมูลออเดอร์และการชำระเงิน — ไม่ต้องขอ consent แบบ opt-in/checkbox แยก เพียงแสดงประกาศ (notice) ให้ลูกค้าทราบก็เพียงพอ
- **สิทธิ์ของเจ้าของข้อมูล**: ลูกค้าสามารถขอลบหรือขอดูข้อมูลออเดอร์ของตัวเองได้ผ่านการติดต่อพนักงาน/เจ้าของร้านโดยตรง เป็นกระบวนการ manual ไม่มีฟีเจอร์ self-service ในระบบ

## เกณฑ์การยอมรับ (Acceptance Criteria)

- [ ] ลูกค้าเห็นประกาศความเป็นส่วนตัวแบบสั้นก่อนเริ่มสั่งอาหาร/จ่ายเงิน โดยระบุข้อมูลที่เก็บและวัตถุประสงค์อย่างชัดเจน
- [ ] Order log, payment transaction log และ table/session log ที่มีอายุเกิน 90 วัน ถูกลบหรือ anonymize แล้ว ไม่มีข้อมูลที่ระบุตัวตนลูกค้าหลงเหลืออยู่
- [ ] มีช่องทางที่ระบุไว้ชัดเจน (เช่น แจ้งพนักงาน/เจ้าของร้าน) ให้ลูกค้าติดต่อเพื่อขอลบหรือขอดูข้อมูลออเดอร์ของตัวเองได้
- [ ] สเปคระบุความเสี่ยงเรื่อง retention 90 วัน เทียบกับข้อกำหนดบัญชี/ภาษี 5 ปีไว้ชัดเจน พร้อมคำแนะนำให้ทบทวนกับนักบัญชีหากมีการตรวจสอบภาษีในอนาคต
