## สร้าง Design System (DESIGN.md)

- **สรุป**: ผู้ใช้แนบภาพโลโก้ร้าน (`CAFÉ • งาย` — "Craft Your Own Specialty Coffee") และขอให้สร้างเอกสาร design system โทน earth tone + minimalist + muji ครอบคลุมอย่างน้อย 4 หัวข้อ: Brand Identity & CI, Design Tokens (สี/ฟอนต์/spacing), UI Components & Patterns, และ UX Guidelines & Rules
- **การตัดสินใจ**: ยังไม่มีเอกสาร design system เดิมในโปรเจกต์ ([[../02-design/01-prototypes/index|01-prototypes]] มีแค่ user-journey.md) จึงสร้างเป็นเอกสารใหม่ทั้งหมด วางไว้ที่ `docs/02-design/01-prototypes/` ตามคำอธิบายของ index.md ที่ระบุว่าโฟลเดอร์นี้เก็บ "Design system เบื้องต้น เช่น สี ฟอนต์ คอมโพเนนต์หลัก"
- **สีที่ดึงมาจากโลโก้**: พื้นครีม, ตัวอักษร/เส้นน้ำตาลเข้ม (espresso/coffee brown), tagline สีฟ้าอมเทาอ่อน — ขยายเป็นพาเลท earth tone เต็มชุด (เทอร์ราคอตต้า, ทราย, olive, ochre, brick) พร้อม token อ้างอิงในตาราง
- **ไฟล์โลโก้**: ผู้ใช้ส่งไฟล์ต้นฉบับมาเก็บไว้ที่ `docs/02-design/01-prototypes/assets/logo.png` แล้ว — อัปเดต DESIGN.md ให้ embed รูปและอ้างอิง path จริงแทนหมายเหตุ placeholder เดิม (ไฟล์เป็น PNG พื้นครีมทึบ ยังไม่มีเวอร์ชันโปร่งใส)
- **เอกสารที่สร้าง**: [[../02-design/01-prototypes/DESIGN|DESIGN.md]] — เชื่อมโยงกลับไปยัง [[../02-design/01-prototypes/user-journey|user-journey]] และสเปคทั้ง 3 ฉบับ ([[../01-requirements/01-spec/20260802-001-dine-in-qr-table-ordering|QR Table Ordering]], [[../01-requirements/01-spec/20260802-002-sales-dashboard|Sales Dashboard]], [[../01-requirements/01-spec/20260802-003-log-retention-pdpa-compliance|Log Retention/PDPA]]) เพื่อให้กติกา UX ผูกกับ business rule ที่มาจริง

## สร้างไฟล์โลโก้พื้นหลังโปร่งใส + แก้ไข tagline

- **สรุป**: ผู้ใช้ขอไฟล์โลโก้เวอร์ชันพื้นหลังโปร่งใส แล้วขอแก้คำใต้โลโก้จาก "Craft Your Own Specialty Coffee" เป็น "Craft Your Own Specialty Recipe"
- **วิธีทำ**: ไม่มีเครื่องมือแก้ไขภาพ (Photoshop/ImageMagick/PIL) ในเครื่อง จึงเขียนสคริปต์ Node.js ถอดรหัส/เข้ารหัส PNG เองเพื่อทำ color-keying แบบ 2 เส้นสี (บนพื้นครีม, ไปยังสีตัวอักษรน้ำตาลกับสีฟ้าอมเทาของ tagline) เพื่อลบพื้นหลังแบบไม่มีขอบขาว/ฟ้าเป็นหลอน (halo) จากนั้นใช้ PowerShell + .NET System.Drawing (Segoe UI, เติม letter-spacing เอง) render คำว่า "Craft Your Own Specialty Recipe" ที่ความละเอียดสูงแล้วย่อขนาดด้วย box-filter ให้พอดีกับพื้นที่ tagline เดิม แล้วต่อ (composite) ทับตำแหน่งเดิมทั้งในไฟล์พื้นทึบและไฟล์โปร่งใส
- **ผลลัพธ์**: ตรวจสอบภาพที่ได้บนพื้นหลังขาวและพื้นหลังเข้มแล้ว ไม่มีขอบเปื้อน/กล่องสีเพี้ยนหลงเหลือ
- **ไฟล์ที่อัปเดต**: `docs/02-design/01-prototypes/assets/logo.png` (พื้นครีมทึบ, tagline ใหม่), `docs/02-design/01-prototypes/assets/logo-transparent.png` (พื้นหลังโปร่งใส, tagline ใหม่ — ไฟล์ใหม่)
- **ข้อจำกัดที่ควรทราบ**: ฟอนต์ tagline เป็นการเลือกฟอนต์ระบบ (Segoe UI) ให้ใกล้เคียงต้นฉบับที่สุดเท่าที่ทำได้ ไม่ใช่ฟอนต์จริงที่นักออกแบบต้นฉบับใช้ — ถ้าต้องการความแม่นยำ 100% ควรขอไฟล์ต้นฉบับ (Figma/Canva/AI) จากผู้ออกแบบมาแก้ไขแทน
- **อัปเดต DESIGN.md**: แก้ tagline ทุกจุดที่อ้างถึงเป็น "Craft Your Own Specialty Recipe" และเพิ่มลิงก์ไฟล์ `logo-transparent.png` ในหัวข้อโลโก้

## เพิ่ม agent/skill สำหรับสร้าง Prototype

- **สรุป**: ผู้ใช้ขอให้สร้าง agent และ skill สำหรับสร้าง UI prototype โดยอ้างอิง Requirement/Backlog/Feature List/User Journey ทั้งหมด แต่ระบุขอบเขตเจาะจงได้ พร้อมกติกา 3 ข้อ: (1) ต้องเสนอแผนให้ผู้ใช้ยืนยันก่อนสร้างเสมอ (2) เมื่อเรียกซ้ำต้องถามผู้ใช้ทุกครั้งว่าจะสร้าง version folder ใหม่หรือแก้ของเดิม พร้อมคำแนะนำ (3) ต้องอ้างอิง DESIGN.md — ถ้าไม่มีให้ถามผู้ใช้สร้างก่อน (เลือกโทนสี/สไตล์/ส่งภาพโลโก้)
- **คำถามที่ถามผู้ใช้ก่อนสร้าง**: รูปแบบของ prototype ที่ agent จะสร้าง — เสนอ 3 ทางเลือก (Markdown wireframe แบบข้อความ / Static HTML-CSS mockup / Mermaid schematic wireframe) ผู้ใช้เลือก **Markdown wireframe (ข้อความ)** เพราะตรงกับหลักการ "ไม่ใช่โค้ดเบส" ของ CLAUDE.md ที่สุด
- **ไฟล์ agent/skill ที่สร้าง**:
  - `.claude/agents/prototype-writer.md` — เขียน/อัปเดต `DESIGN.md` (เมื่อยังไม่มี, รับ style input จาก skill) และเขียน prototype แต่ละหน้าจอเป็น Markdown wireframe (ASCII box layout) ใต้ `docs/02-design/01-prototypes/prototypes/v{N}/` แต่ละหน้าจอ map กลับไปยัง component/token ของ DESIGN.md และ requirement/journey step ที่เกี่ยวข้อง
  - `.claude/skills/create-prototype/SKILL.md` — orchestrate: กำหนดขอบเขต → เช็ค/สร้าง DESIGN.md (ถามผู้ใช้ถ้ายังไม่มี) → ถามผู้ใช้ทุกครั้งเรื่อง version folder ใหม่/แก้ของเดิม (มีคำแนะนำ) → เสนอแผนให้ยืนยัน → เรียก `prototype-writer` → อัปเดต cross-link → log ผล
- **โครงสร้างไฟล์ที่วางไว้**: `docs/02-design/01-prototypes/prototypes/v{N}/index.md` (สรุปเวอร์ชัน + ตารางหน้าจอ) และไฟล์ `{running-no}-{ascii-slug}.md` หนึ่งไฟล์ต่อหนึ่งหน้าจอ
- **ยังไม่ได้รันจริง**: เอกสารนี้เป็นการสร้างเครื่องมือ (agent/skill) ตามที่ผู้ใช้ขอ ยังไม่มีการเรียกใช้งานสร้าง prototype จริงในรอบนี้

## เพิ่ม agent/skill สำหรับสร้าง Test Plan

- **สรุป**: ผู้ใช้ขอให้แนะนำ sub agent, skill และเอกสารที่ควรมีสำหรับทำ test plan/test case/acceptance criteria แล้วขอให้สร้างจริงตามคำแนะนำ
- **แนวทางที่แนะนำและสร้างตาม**: ยึด pattern เดียวกับ `create-prototype`/`prototype-writer` — แยก interactive part (กำหนดขอบเขต, ตัดสินใจ new-file-vs-update, เสนอแผน/ยืนยัน) ไว้ที่ skill ในบทสนทนาหลัก แล้วส่งงานเขียนไฟล์จริงให้ subagent
- **ไม่สร้างเอกสารประเภทใหม่**: acceptance criteria ยังคงอยู่ที่สเปคใน `01-requirements/01-spec/` เป็น source of truth เดิม — test plan แค่ทำ traceability กลับไปหาเกณฑ์เหล่านั้น (เพิ่มตาราง "Acceptance Criteria Coverage" ในทุก test plan เพื่อให้เห็นชัดว่าเกณฑ์ข้อไหนยังไม่มี test case ครอบคลุม แทนที่จะสร้างเอกสาร acceptance-criteria แยกซ้ำซ้อน)
- **ความแตกต่างจาก create-prototype**: test plan เป็นเอกสารต่อฟีเจอร์แบบ living document ไม่ใช่ versioned snapshot แบบ prototype จึงไม่มีคำถาม "version folder ใหม่" ทุกรอบ — แทนที่ด้วยการตัดสินใจ "เพิ่ม/แก้ไฟล์เดิม" (ค่าเริ่มต้นที่แนะนำ) เทียบกับ "เขียนใหม่ทั้งไฟล์" (เฉพาะเมื่อสเปคเปลี่ยนจนต้องทิ้ง test case/สถานะเดิม)
- **ไฟล์ agent/skill ที่สร้าง**:
  - `.claude/agents/test-plan-writer.md` — เขียน/อัปเดต test plan ต่อฟีเจอร์ใต้ `docs/03-testing/01-test-plan/{YYYYMMDD}-{spec-running-no}-{spec-slug}.md` ตาม structure เดิมที่มีอยู่แล้ว (Objective, Scope, Test Data, Test Case table, Acceptance Criteria Coverage table ใหม่, หมายเหตุช่องว่าง, เอกสารที่เกี่ยวข้อง) — ห้ามฟันธงพฤติกรรมที่สเปคไม่ได้ระบุ (มาร์ก Blocked แทน) และห้ามเขียนผลทดสอบจริง (ผ่าน/ไม่ผ่าน) ลงในเอกสารนี้ — ผลทดสอบเป็นคนละ stage (`02-test-result/`)
  - `.claude/skills/create-test-plan/SKILL.md` — orchestrate: กำหนดขอบเขต (ค่าเริ่มต้น = ทุกฟีเจอร์ Must/Should have ที่ยังไม่มี test plan) → อ่านสเปค/journey/prototype ที่เกี่ยวข้อง → ตัดสินใจ new-file-vs-update-existing ต่อฟีเจอร์ (พร้อมคำแนะนำ) → เสนอแผน (ไฟล์ปลายทาง, test case ที่จะเพิ่ม, ช่องว่างที่พบ) ให้ผู้ใช้ยืนยัน → เรียก `test-plan-writer` → อัปเดต cross-link ที่ `01-test-plan/index.md` (แปลงเป็นตารางเมื่อมีมากกว่า 1 ไฟล์) → log ผล
- **ยังไม่ได้รันจริง**: เอกสารนี้เป็นการสร้างเครื่องมือ (agent/skill) ตามที่ผู้ใช้ขอ ยังไม่มีการเรียกใช้งานสร้าง test plan จริงในรอบนี้ — ฟีเจอร์ 001 มี test plan ต้นแบบอยู่แล้ว ([[../03-testing/01-test-plan/20260815-001-dine-in-qr-table-ordering|test plan เดิม]]) ที่ใช้เป็นตัวอย่างโครงสร้างในการออกแบบ agent นี้
