# Log — 2026-08-02

## สร้างเอกสาร requirement: ระบบสั่งกาแฟที่โต๊ะด้วย QR Code

- **สรุป**: ผู้ใช้แจ้ง requirement ดิบว่าต้องการให้ลูกค้าสั่งกาแฟได้ที่โต๊ะ ได้สอบถามเพิ่มเติม 3 เรื่อง (วิธีสั่ง / การชำระเงิน / การแจ้งครัว) แล้วสรุปเป็นเอกสารสเปคฉบับแรกของโปรเจกต์
- **การตัดสินใจ**: ไม่มีเอกสาร requirement เดิมในระบบ ([[../01-requirements/01-spec/index|01-spec]] มีแค่ index.md และ [[../01-requirements/backlog|backlog]] ว่างเปล่า) จึงสร้างเป็นเอกสารใหม่ทั้งหมด ไม่ต้องพิจารณาแก้ไข/แทนที่เอกสารเดิม
- **เอกสารที่สร้าง**: [[../01-requirements/01-spec/20260802-001-dine-in-qr-table-ordering|20260802-001-dine-in-qr-table-ordering]]
- **รายละเอียดที่ยืนยันกับผู้ใช้**:
  - วิธีสั่ง: สแกน QR code ที่โต๊ะ สั่งผ่านมือถือลูกค้าเอง
  - การชำระเงิน: จ่ายทันทีก่อนออเดอร์เข้าครัว
  - การแจ้งครัว: ขึ้นจอออเดอร์แบบเรียลไทม์ (KDS)
- **อัปเดต backlog**: เพิ่มแถวลำดับที่ 001 สถานะ Backlog ใน [[../01-requirements/backlog|backlog]]

## สร้างเอกสาร requirement: Dashboard ดูยอดขาย

- **สรุป**: ผู้ใช้แจ้ง requirement ดิบว่าต้องการเพิ่ม dashboard ดูยอดขาย เมื่อถามคำถามชี้ขาด 3 ข้อ (ผู้ใช้งาน / ข้อมูลที่แสดง / ช่วงเวลาย้อนหลัง) แล้วผู้ใช้ให้ Claude แนะนำแนวทางแทนการเลือกเอง จึงสรุปทางเลือกที่เหมาะกับร้านขนาดเล็กสาขาเดียว แล้วเขียนเป็นสเปค
- **แนวทางที่แนะนำและใช้**:
  - ผู้ใช้งาน: เจ้าของร้าน/ผู้จัดการเท่านั้น
  - ข้อมูลหลัก: ยอดขายรวมตามช่วงเวลา + แยกตามเมนู
  - ช่วงเวลาย้อนหลัง: รายวัน/รายสัปดาห์/รายเดือน (ยังไม่ทำ custom date range)
- **การตัดสินใจ**: ไม่พบเอกสาร requirement เดิมที่ทับซ้อนใน [[../01-requirements/01-spec/index|01-spec]] (มีแค่เอกสารระบบสั่งที่โต๊ะ) จึงสร้างเป็นเอกสารใหม่ และเชื่อมโยงกลับไปยังเอกสารระบบสั่งที่โต๊ะในฐานะแหล่งข้อมูลยอดขาย
- **เอกสารที่สร้าง**: [[../01-requirements/01-spec/20260802-002-sales-dashboard|20260802-002-sales-dashboard]]
- **อัปเดต backlog**: เพิ่มแถวลำดับที่ 002 สถานะ Backlog ใน [[../01-requirements/backlog|backlog]]

## สร้างเอกสาร requirement: การเก็บ Log และการปฏิบัติตาม PDPA

- **สรุป**: ผู้ใช้แจ้ง requirement ที่ผ่านการ clarify มาแล้วเรื่องการเก็บ log (order log, payment transaction log, table/session log) และการปฏิบัติตาม PDPA สำหรับระบบที่มีอยู่แล้วทั้งสองฟีเจอร์ ([[../01-requirements/01-spec/20260802-001-dine-in-qr-table-ordering|ระบบสั่งกาแฟที่โต๊ะด้วย QR Code]] และ [[../01-requirements/01-spec/20260802-002-sales-dashboard|Dashboard ดูยอดขาย]]) โดยเน้นหลักการ "ทำเท่าที่จำเป็น"
- **การตัดสินใจ**: อ่านสเปคเดิมทั้งสองฉบับแล้วพบว่าไม่มีฉบับใดพูดถึง log retention หรือ PDPA เลย และประเด็นนี้เป็นมุมมองเชิง data/privacy ที่ตัดขวางทั้งสองฟีเจอร์ ไม่ใช่ requirement เฉพาะของฟีเจอร์ใดฟีเจอร์หนึ่ง จึงสร้างเป็นเอกสารสเปคใหม่แยกต่างหาก (ไม่แก้ไขสเปคเดิม ไม่ archive อะไร) พร้อมเชื่อม wikilink กลับไปยังสเปคทั้งสองฉบับในฐานะแหล่งข้อมูล log
- **เอกสารที่สร้าง**: [[../01-requirements/01-spec/20260802-003-log-retention-pdpa-compliance|20260802-003-log-retention-pdpa-compliance]]
- **รายละเอียดที่ยืนยันกับผู้ใช้**:
  - Retention period: 90 วัน (3 เดือน) สำหรับ log ทั้ง 3 ประเภทเท่ากันหมด — ผู้ใช้รับทราบความเสี่ยงเรื่องกฎหมายบัญชี/ภาษีที่กำหนดให้เก็บเอกสาร 5 ปี และยืนยันเลือก 90 วันอย่างจงใจ พร้อมบันทึกคำแนะนำให้ทบทวนกับนักบัญชีหากมีการตรวจสอบภาษีในอนาคต
  - Privacy notice แบบข้อความสั้น แสดงตอนสแกน QR ก่อนสั่ง/จ่ายเงิน ไม่ใช้ consent แบบ opt-in/checkbox — ใช้ฐานกฎหมาย "จำเป็นเพื่อปฏิบัติตามสัญญา"
  - สิทธิ์เจ้าของข้อมูล: ใช้ช่องทาง manual (ติดต่อพนักงาน/เจ้าของร้าน) ไม่ทำฟีเจอร์ self-service
  - Out of scope ที่ระบุชัดเจน: consent management platform, audit log การเข้าถึง dashboard, DPA กับผู้ให้บริการ payment, self-service ลบ/ดาวน์โหลดข้อมูล, แผนรับมือ data breach, การแยก retention ตามกฎหมายบัญชี
- **อัปเดต backlog**: เพิ่มแถวลำดับที่ 003 สถานะ Backlog ใน [[../01-requirements/backlog|backlog]]
