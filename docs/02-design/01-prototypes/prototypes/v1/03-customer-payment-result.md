## บริบท

- มาจากขั้นตอน **E** ใน [[../../user-journey|user-journey]] (หัวข้อ "ลูกค้าสั่งกาแฟที่โต๊ะด้วย QR Code") ซึ่งแตกสองทาง: จ่ายสำเร็จ → **F** (ออเดอร์ส่งเข้าจอ KDS) / จ่ายไม่สำเร็จ → **G** (ออเดอร์ไม่ถูกส่งเข้า KDS)
- เกณฑ์การยอมรับ/กฎที่ต้อง satisfy: [[../../../../01-requirements/01-spec/20260802-001-dine-in-qr-table-ordering|QR Table Ordering]] ข้อ 3 และกฎทางธุรกิจ "การชำระเงิน" — "ระบบต้องยืนยันว่าชำระเงินสำเร็จก่อนจึงจะส่งออเดอร์เข้าคิวของ KDS ได้ — ออเดอร์ที่ยังไม่จ่ายเงินต้องไม่ปรากฏบนจอครัว" ตรงกับ UX rule "ลำดับจ่ายก่อนเข้าครัว" ใน DESIGN.md
- หน้าจอนี้มี **2 สถานะทางเลือก** (แสดงแยกกัน ไม่ปรากฏพร้อมกันจริงในหน้าเดียว — แสดงคู่กันในเอกสารนี้เพื่อเทียบ layout)

## Wireframe (text-based)

**สถานะ A — ชำระเงินสำเร็จ**

```
┌───────────────────────────────────────┐
│  [Table Badge: โต๊ะ 5]                  │
├───────────────────────────────────────┤
│              ✓                         │
│         (ไอคอนเรียบสีเดียว)              │
│                                         │
│         ชำระเงินสำเร็จ                    │
│                                         │
│  [Order Status Tag: ส่งเข้าครัวแล้ว]       │
│         (สีสถานะ success)               │
│                                         │
│    ออเดอร์ถูกส่งเข้าครัวแล้ว                │
│    กรุณารอรับที่โต๊ะ 5                     │
└───────────────────────────────────────┘
```

**สถานะ B — ชำระเงินไม่สำเร็จ**

```
┌───────────────────────────────────────┐
│  [Table Badge: โต๊ะ 5]                  │
├───────────────────────────────────────┤
│              ✕                         │
│         (ไอคอนเรียบสีเดียว)              │
│                                         │
│         ชำระเงินไม่สำเร็จ                  │
│                                         │
│  [Order Status Tag: ยังไม่เข้าครัว]        │
│         (สีสถานะ error)                 │
│                                         │
│    ออเดอร์นี้ยังไม่ถูกส่งเข้าครัว            │
│    กรุณาลองชำระเงินใหม่อีกครั้ง              │
├───────────────────────────────────────┤
│  [Primary Button: ลองชำระเงินใหม่]        │
│  [Secondary/Ghost Button: กลับไปแก้ไขออเดอร์]│
└───────────────────────────────────────┘
```

## Components ที่ใช้ (อ้างอิง DESIGN.md)

| Component | Token/สี | หมายเหตุ |
|---|---|---|
| Table Badge | `color-text-primary`, `text-h2` | แสดงต่อเนื่องทั้งสองสถานะ ตาม UX rule "ความชัดเจนของหมายเลขโต๊ะ" |
| Order Status Tag | `color-success` (สถานะ A) / `color-error` (สถานะ B), พื้น `color-surface-alt` เท่านั้น ไม่ใช้ solid fill พื้นที่ใหญ่ | สื่อสถานะให้ตรงกับกฎ "ลำดับจ่ายก่อนเข้าครัว" — ห้าม tag ขึ้นว่า "เข้าครัวแล้ว" ถ้ายังไม่ยืนยันว่าจ่ายสำเร็จ |
| Primary Button | `color-accent-primary`, radius 8px | ปรากฏเฉพาะสถานะ B (ลองชำระเงินใหม่) — สถานะ A ไม่มี primary action เพิ่มเติมเพราะออเดอร์เสร็จสิ้นแล้ว ตาม UX rule "1 primary action ต่อหน้าจอ" |
| Secondary/Ghost Button | เส้นขอบ `color-border` | action รอง "กลับไปแก้ไขออเดอร์" เฉพาะสถานะ B |

## State / Edge cases

- **ช่องว่างที่พบ** (อ้างอิงจาก [[../../user-journey|user-journey]] โดยตรง): "สเปคยืนยันว่าออเดอร์ที่จ่ายไม่สำเร็จจะไม่เข้า KDS แต่ไม่ได้ระบุ UX ฝั่งลูกค้าหลังจ่ายไม่สำเร็จ (เช่น ข้อความแจ้งเตือน / ให้ลองจ่ายใหม่กี่ครั้ง) — ควรชี้แจงเพิ่มเติมกับเจ้าของร้านก่อนนำ diagram นี้ไปออกแบบหน้าจอจริง" ปุ่ม "ลองชำระเงินใหม่" ในไวร์เฟรมนี้เป็นเพียง placeholder ขั้นต่ำสุด ไม่ได้ยืนยันจำนวนครั้งที่ลองใหม่ได้ หรือข้อความแจ้งเตือนที่แน่นอน
- **สถานะ A**: ต้องไม่แสดง Order Status Tag ว่า "เข้าครัวแล้ว" ก่อนระบบยืนยันว่าจ่ายเงินสำเร็จจริง (ตรงตาม UX rule ที่อ้างถึงข้างต้น) — ในไวร์เฟรมนี้ tag จะขึ้นหลังชำระสำเร็จเท่านั้น
- **สถานะ B**: ระบุชัดเจนว่าออเดอร์ "ยังไม่ถูกส่งเข้าครัว" เพื่อไม่ให้ลูกค้าเข้าใจผิดว่าออเดอร์เข้าคิวแล้ว
