# หน้ายืนยันออเดอร์ + ชำระเงิน (ลูกค้า)

## บริบท

- มาจากขั้นตอน **D → E** ใน [[../../user-journey|user-journey]] (หัวข้อ "ลูกค้าสั่งกาแฟที่โต๊ะด้วย QR Code"): เลือกเมนูเสร็จแล้ว → ยืนยันออเดอร์ + ชำระเงินในขั้นตอนต่อเนื่องเดียวกัน
- เกณฑ์การยอมรับที่ต้อง satisfy: [[../../../../01-requirements/01-spec/20260802-001-dine-in-qr-table-ordering|QR Table Ordering]] ข้อ 2 — "ลูกค้าสั่งเมนูและชำระเงินสำเร็จได้ในขั้นตอนต่อเนื่องเดียวกัน" (สเปคยกตัวอย่างช่องทางชำระเงินว่า "เช่น QR พร้อมเพย์" — เป็นตัวอย่าง ไม่ใช่ข้อบังคับว่าต้องมีเฉพาะช่องทางนี้เท่านั้น)

│  │ ลาเต้ x2                  ฿130  │     │
│  ├───────────────────────────────┤     │
│  │ อเมริกาโน่ x1              ฿50   │     │
│  └───────────────────────────────┘     │
├───────────────────────────────────────┤
│  รวมทั้งหมด                     ฿235    │

## Components ที่ใช้ (อ้างอิง DESIGN.md)

| Component | Token/สี | หมายเหตุ |
|---|---|---|
| Table Badge | `color-text-primary`, `text-h2` | ยังคงแสดงต่อเนื่องจากหน้าเมนู ตาม UX rule "ความชัดเจนของหมายเลขโต๊ะ" |
| Primary Button | `color-accent-primary`, ตัวอักษรสีครีม, radius 8px | ปุ่มเดียวของหน้านี้ — รวมขั้นตอน "ยืนยันออเดอร์" และ "ชำระเงิน" เป็น action เดียวกัน ตรงตามเกณฑ์การยอมรับข้อ 2 และ UX rule "1 primary action ต่อหน้าจอ" |
| Secondary/Ghost Button | เส้นขอบ `color-border`, ตัวอักษร `color-text-secondary` | action รอง "กลับไปแก้ไขเมนู" ไม่แย่งความสำคัญจาก Primary Button |

## State / Edge cases

- **รายการว่าง**: สเปคไม่ได้ระบุพฤติกรรมเมื่อลูกค้าพยายามเข้าหน้านี้โดยไม่มีรายการในตะกร้า — ไม่ฟันธงพฤติกรรม (เช่น จะ block หรือ redirect กลับหน้าเมนูอัตโนมัติหรือไม่)
- **ช่องทางชำระเงิน**: สเปคระบุ "เช่น QR พร้อมเพย์" เป็นตัวอย่างเท่านั้น ไม่ได้ยืนยันว่าต้องรองรับเฉพาะ PromptPay หรือช่องทางอื่นด้วยหรือไม่ — ควรยืนยันกับเจ้าของร้านก่อนล็อกดีไซน์ของขั้นตอนชำระเงินจริง
- ผลลัพธ์หลังกดปุ่มนี้ (สำเร็จ/ไม่สำเร็จ) ดูรายละเอียดที่ [[03-customer-payment-result|03-customer-payment-result]]
